Migration ethers 2.0.14 (archiviert) → alloy 2.4 — Verhalten byte-identisch
==============================================================================

Ziel: Die archivierte ethers-Dependency komplett entfernen und durch alloy (2.4.1, aktueller Stable) ersetzen. Kein CLI- oder Wire-Format-Change: Envelope, Signaturformat (0x + r(64) + s(64) + v(2), v=27/28), Fehler-Strings und alle 7 Regressionstests bleiben unverändert gültig.

1. Cargo.toml
------------
- Entfernen: `ethers = { version = "2.0.14", features = ["eip712","abigen","rustls"] }` und die direkte `reqwest`-Dependency (wird in `src/` nicht direkt genutzt; alloy bringt sein eigenes reqwest 0.13 mit, Default = reines rustls).
- Neu: `alloy = { version = "2.4", features = ["eip712"] }` — Defaults sind bereits `reqwest` + `reqwest-rustls-tls` + `essentials` (contract, provider-http, rpc-types, signer-local); damit bleibt der Build frei von native-tls/openssl-sys.
- `rand = "0.8"` bleibt (nur noch für den 32-Byte-Nonce).
- Version: 0.2.2 → 0.3.0.

2. src/x402.rs — Kern der Migration
-----------------------------------
- EIP-712 ohne den serde_json-Umweg: `alloy::sol!`-Struct `TransferWithAuthorization { address from; address to; uint256 value; uint256 validAfter; uint256 validBefore; bytes32 nonce; }` (pub für die Tests).
- Domain: `Eip712Domain::new(Some(name), Some(version), Some(U256::from(chain_id)), Some(token), None)`.
- Signing: `wallet.sign_typed_data(&payload, &domain).await?` → `Signature::as_bytes()` = exakt die 65 Bytes r||s||v (v=27+y_parity) — ersetzt `format!("0x{:064x}{:064x}{:02x}", sig.r, sig.s, sig.v)` durch `format!("0x{}", hex::encode(sig.as_bytes()))`, identischer Output.
- Kleinere Umstellungen: `U256::from_dec_str(amount)` → `amount.parse::<U256>()?`; Address/U256/`{:#x}` unverändert (alloy formattiert identisch klein-hex).
- `create_payment` vereinfachen: kein `Arc<SignerMiddleware<…>>`-Parameter mehr; stattdessen `chain_id: u64` (main.rs holt sie autoritativ + validiert über `http_provider()` → RPC-Chain-ID-Prüfe bleibt erhalten). `build_payment(wallet: &PrivateKeySigner, chain_id, …)` — der netzwerkfreie, testbare Kern bleibt.
- Verbatim-Echo-Logik (asset/payTo, accepted-json, validAfter=0, validBefore=now+timeout) bleibt unangetastet.

3. src/store.rs
--------------
- `LocalWallet` → `alloy::signers::local::PrivateKeySigner`; `LocalWallet::new(&mut OsRng)` → `PrivateKeySigner::random()`; `wallet.signer().to_bytes()` → `wallet.to_bytes()`; `H160` → `alloy::primitives::Address`.
- `with_chain_id` entfällt (alloys Recommended-Filler füllt die Chain-ID beim Tx-Signing aus dem RPC selbst); `WalletContext { wallet: PrivateKeySigner, address: Address }`.

4. src/evm.rs
------------
- Provider: `Provider::<Http>::try_from(url)` → `ProviderBuilder::new().connect_http(Url)`; `get_chainid().as_u64()` → `get_chain_id()` (liefert u64 direkt); `get_balance(addr, None)` → `get_balance(addr)`.
- `SignerMiddleware` entfällt: `provider_with_wallet` baut `ProviderBuilder::new().wallet(signer).connect_http(url)`.
- `abigen!(ERC20, …)` → `alloy::sol!`-Interface `IERC20` (decimals/balanceOf/transfer); Contract-Bindings ohne Transport-Generic.
- `TransactionRequest::new().to().value()` → `TransactionRequest::default().with_to().with_value()` (mit `use alloy::network::TransactionBuilder`).
- Units: `parse_ether`/`parse_units` jetzt fallibel (`?`), `format_units(bal, "ether")` bzw. dezimale Variante für ERC20.
- Pending/Receipt: `pending.await? → Option<Receipt>` → `send_transaction(tx).await?.get_receipt().await?`, Fehler weiterhin als `"transaction dropped from mempool"` gemappt; Tx-Hash-Ausgabe `{:?}` bleibt `0x…`.
- Funktions-Signaturen generisch (`P: Provider<Ethereum>`) statt konkreter FillProvider-Typen (die sind in alloy praktisch unbenennbar).

5. src/main.rs
-------------
Nur Klebstoff: `ctx.address {:#x}` bleibt; CreatePayment ruft statt `provider_with_wallet` nur noch `evm::http_provider()` für die (validierte) Chain-ID auf und übergibt sie an `create_payment(chain_id, &ctx.wallet, …)`.

6. tests/x402_regression.rs
---------------------------
- Wallet-Helper: `PrivateKeySigner::from_bytes(&B256::from_slice(&hex…))` statt `LocalWallet::from_bytes().with_chain_id(8453)` (Chain-ID geht als Parameter an `build_payment`, wie eh und je).
- Recovery-Test: statt ethers `TypedData` + `recover_typed_data` das公开的 `TransferWithAuthorization`-Struct + Domain aus dem dekodierten Payload rekonstruieren, `payload.eip712_signing_hash(&domain)` + `Signature::from_raw_array(&bytes)` + `sig.recover_address_from_prehash(&digest) == wallet.address()`. Alle 7 Assertions (Format, validAfter=0, verbatim Echos, CAIP-2, v1/v2-Shapes) bleiben inhaltlich identisch.

8. Risiken & Fallbacks
----------------------
- **aws-lc-rs/CMake:** Alloys rustls-Default baut den aws-lc-rs-Provider (C-Code; CMake auf Windows nötig). CI-Runner (windows-latest) haben CMake vorinstalliert. Falls der lokale Build an aws-lc scheitert: `scoop install cmake` (NASM nicht nötig, aws-lc-rs baut prebuilt/noasm auf MSVC) — oder kurzfristig Rustls-Provider-Konfiguration. Wird beim Build sofort sichtbar.
- **Cargo.lock-Churn:** kompletter Austausch des Dependency-Baums (ethers raus, alloy rein) — erwartet und im Commit dokumentiert.
- **Bytes-Identität:** kritischster Punkt ist die EIP-712-Signatur; abgesichert durch Test #4 (Signatur-Recovery) + Testformat-Assertions (132 Zeichen) und Smoke-Dekodierung.
- Keine Doku-Änderungen nötig (README/wallet.md/llms.txt nennen ethers nicht).

9. Abschluss
------------
Commit („migrate ethers → alloy 2.4") + Push auf main, wie heute üblich nach Freigabe.
